## Что внутри

| Что | Зачем |
|---|---|
| `android_act` | Действие на экране + ожидание, пока UI «успокоится» (≥500 мс без изменений) + компактный снимок. Вместо цепочки `tap → screen → screen`. Возвращает `changed`, поэтому агент видит, что тап не сработал, и не повторяет его вслепую. Элементы имеют `[ref]` → `tap ref=N expect="текст"`. |
| `agent_memory` | Долговременная память между чатами: add / search / list / delete / pin. Файл `<files>/agent-memory/notes.json`, атомарная запись, лимиты (200 заметок, ≤500 символов), дубликаты объединяются. В начале хода заметки показываются модели (закреплённые первыми) — как данные, не как команды. Выключить: `DSH_MEMORY=off`, свой файл: `DSH_MEMORY_FILE`. |
| `android_wait_until` | Ждёт текст / исчезновение текста / смену приложения вместо `sleep`. Прерывается по `signal` (кнопка «стоп» работает сразу). ⚠️ Имя уже занято плагином `dsh-tool-agent-plus` — см. «Риски». |
| `android_find` | Возвращает только совпавшие элементы — не тащит всё дерево в контекст. |
| guard | Бюджет шагов на ход (по умолчанию 60), детектор повторов (3× → предупреждение, 6× → стоп), пинг-понг A,B,A,B, серия ошибок. В README цикла: *«No built-in turn budget»* (подтверждено: dsh-agent-loop/README.md:202). |
| `lib/policy.js` | Классификатор shell-команд `read / write / destructive / forbidden` + `enforce()`. `forbidden` — всегда запрет: убить `node`, удалить/очистить собственный пакет или Shizuku, `rm -rf /`, `settings put global adb_enabled 0`. |
| `lib/a11y-boot.js` | При старте движка возвращает службу спец. возможностей, которую система вычищает при перезапуске приложения (проверено: OFF → ON за 88 мс). Выключить: `DSH_A11Y_BOOT=off`. |
| `patches/*.diff` | Исправления найденных багов в 04/05/06 (см. ниже). Только для сборки из исходников репозитория. |

## Установка (исправлено)

**Сторонний плагин = бандл профиля.** Копировать в `dshroot/lib/node_modules/@deepseek-ai/...` бесполезно:
приложение восстанавливает дерево `dshroot` из APK и чистит незнакомые пакеты под scope `@deepseek-ai`
(проверено ранее, `KERNEL-EXTENSIONS-2026-09-29.md`; MainActivity: FORCE_OVERWRITE-белый список + очистка).

1. Пакет: `payload/dshhome/profiles/web/node_modules/dsh-tool-agent-kit/`
   - имя **без** scope `@deepseek-ai` (иначе приложение вычистит пакет);
   - в `package.json` обязательно `"dsh": {"bundle": {"patch": "./cordis.patch.yml"}}`;
   - `cordis.patch.yml`: `- insert:` + `id: tool-agent-kit`, `name: dsh-tool-agent-kit`.
2. Прописать `dsh-tool-agent-kit` в `payload/dshhome/profiles/web/package.json` → `dsh.profile.bundles`.
3. Проверка без перезапуска приложения: `dsh --profile web --dump-config` (секция `dsh-tool-agent-kit`).
4. Инструменты перечитываются только при старте движка — правка JS на ходу не подхватывается.
5. Переменные окружения node-процесса (в `MainActivity`):
   - `DSH_APPROVAL=risky` — подтверждение только на `destructive`; `auto` (по умолчанию) — как раньше; `ask` = `SHIZUKU_APPROVE=ask`;
   - `DSH_MAX_STEPS=60` — бюджет шагов; `DSH_GUARD=off` — выключить guard;
   - `DSH_PROTECTED_PKGS=a.b,c.d` — доп. защищённые пакеты.

1. `lib/policy.js`: редирект-проверка была `/>\{1,2\}\s*[^\s&|;]/` (экранированные скобки = поиск литерала `{1,2}`), из-за чего `cat /a > /sdcard/b.txt` классифицировался как `read`. Стало `/>{1,2}\s*[^\s&|;]/`. Именно на этом падал один из 29 тестов.

## Планировщик: очередь и режим «умный будильник» (01.10.2026)

**Что работает сейчас (этап 1).** Плагин держит собственную очередь задач (`agent-memory/schedule-queue.json`) —
единственный источник правды. Из журнала приложения задачи ЗАХВАТЫВАЮТСЯ (со своими id и статусами), в слот 0
будильника всегда ставится ТОЛЬКО ближайшая задача (или заглушка `noop` на 2099, если очередь пуста). Поэтому
затирание задач исчезло, а отмена стала настоящей: `android_schedule_cancel` убирает задачу из очереди, и захват
её больше не возвращает (надгробие).

**Исполнение ВЫКЛЮЧЕНО по умолчанию** — это осознанное требование безопасности, а не недоделка:
`DEFAULTS.execute = false` в `lib/schedule-runner.js`. Пока не готовы (а) жёсткий allowlist инструментов для сессии
по расписанию и (б) подтверждение владельца, минуя агента, раннер НЕ отправляет задачи в модель. Даже если после
обновления ядра найдётся сервис сессий, исполнение не начнётся само. Ручной выключатель: `DSH_SCHEDULE_EXECUTE=1`
(и общий `DSH_SCHEDULE_RUNNER=off`, чтобы выключить раннер целиком).

**Почему нельзя иначе.** `/schedule` на `127.0.0.1` работает без токена: любое приложение на телефоне может записать
задачу в журнал. Если такую задачу исполнить со всеми инструментами агента, включая Shizuku shell, это готовый канал
выполнения чужого кода. Плюс сам агент уязвим к инъекции из внешнего контента и может сам поставить «свою» задачу —
поэтому одного признака «задача из нашего инструмента» недостаточно.

**Этапы (по согласованию с ревью):**
1. Очередь, слот 0, список, настоящая отмена и режим «напоминание без автоисполнения» — сделано (этот файл).
2. Автоисполнение для задач профиля `readonly` с жёстким allowlist (allowlist, а не denylist; без связки
   «чтение + сеть»; `bash` в профиль не входит никогда; `android_schedule*` в allowlist не входит) — после живого
   негативного теста «сессия с readonly не может вызвать shell».
3. Профиль `full` и задачи из журнала — только после проверенного канала подтверждения человеком (ожидание с
   отклонением по таймауту, субъект решения — владелец; агент не может ответить на запрос сам).

**Отдельно (для Issue, без пересборки приложения не закрыть):** `/schedule` без токена; приложение при срабатывании
будильника шлёт пустое уведомление, потому что его исполнитель не проходит авторизацию движка (401) и вызывает
устаревший маршрут `/api/session.create` (404 с валидной cookie).
**Важное ограничение «настоящей отмены».** Она верна для задач, которые плагин успел перехватить ДО первого
срабатывания: тогда живой будильник лежит в слоте 0 и перевзведение заменяет его. Но после первого срабатывания
повторная задача уходит в слот `taskId.hashCode()` (так делает AlarmReceiver) и **перепланирует себя сама** —
ни отмена в очереди, ни правка журнала её не остановят. Такие «хвосты» снимаются только остановкой приложения:
`am force-stop com.deepseek.harness` (снимает все будильники пакета разом, но убивает и движок), после чего
очередь взводит заглушку или ближайшую задачу. Пока хвосты живы, они продолжают присылать пустые уведомления —
это видимый признак.

**Источник флага `execute`:** только `DEFAULTS.execute` в коде и переменная окружения движка
`DSH_SCHEDULE_EXECUTE=1`. **Из файлов он не читается** — значит записать его через файловые инструменты агента нельзя.

**Чего выключатель НЕ делает (важно).** `execute` — это защита от СЛУЧАЙНОГО включения (например, после
обновления ядра, когда внезапно найдётся сервис сессий), но **не граница безопасности против инъекции**: код плагина
лежит в каталоге профиля, который доступен тому же uid, а значит и агенту — `DEFAULTS.execute` или конфигурацию
запуска движка можно переписать. Настоящая граница — только **проверяемый вне файлов канал подтверждения человеком**.
Если такого канала не появится, этап 2 (автоисполнение) должен остаться выключенным навсегда — это нормальный итог,
а не недоделка.
